## 2. DAA — детальний аудит

### 2.1 Реалізація (`mhcoin/consensus/difficulty.py`)

**До висоти 1500 (`DIFFICULTY_BTC_ACTIVATION_HEIGHT`):**

1. Retarget **після кожного блоку**.
2. Вікно до **30** timestamp’ів предків (`DIFFICULTY_LEGACY_WINDOW`).
3. `actual_timespan = ts_last − ts_first`; від’ємне → 0.
4. Clamp: `[expected/4 … expected×4]`.
5. Новий target = `old × adjusted / expected`, потім **damping 1/16** відхилення.
6. Обмеження `1 … POW_LIMIT`; canonical compact `nBits` без sign-bit.

**З висоти ≥ 1500:**

- Retarget лише коли `next_height % 2016 == 0`.
- Повний крок (без damping), той самий clamp ×1/4..×4.
- Між epoch — `nBits` копіюється з parent.

**Додаткові консенсусні захисти** (`validation.py` + `chain.py`):

| Правило | Значення |
|---------|----------|
| Exact bits | `header.bits == get_next_work(...)` |
| PoW | `HASH256(header) ≤ target` (LE) |
| MTP | `timestamp > MTP` (вікно 11) |
| Future | `timestamp ≤ now + 7200` (`MAX_FUTURE_BLOCK_TIME`) |
| POW_LIMIT | target ≤ genesis target |

### 2.2 Перевірка на Mainnet

- Активних блоків: **1169** (висоти 0…1168).
- Side / orphan index (`status=0`): **20** блоків.
- Повний реcompute `get_next_work` для кожного активного блоку: **0 розбіжностей**.
- Compact round-trip: **0 помилок**.
- MTP / negative intervals: **0**.

**Висновок DAA:** реалізація відповідає заявленим правилам; історичний Mainnet валідний відносно поточного коду 0.4.2.0.

### 2.3 Реакція на різкий хешрейт (синтетика, без запису в Mainnet)

Стартові bits класу tip (`0x1d0739be`, ~567× genesis):

| Сценарій | Результат |
|----------|-----------|
| Хешрейт ×10 (інтервал 60 с) | ~**49** блоків → target ≈ **/10** (damping) |
| Хешрейт ÷10 (інтервал 6000 с) | ~**79** блоків → target ≈ **×549**, майже до `POW_LIMIT` (×567) |
| Довгий stall (24 год у вікні) | один крок ≈ **×1.1875** (не миттєвий ×4) |
| Усі timestamp рівні | target **жорсткішає** (~×0.953) через clamp `/4` + damping |
| Extreme stretch timestamp | ease обмежений clamp ×4 + damping (~×1.1875/крок) |

Після активації BTC-DAA (синтетика до h=2016): при вікні з інтервалом 60 с epoch-retarget дає **target_ratio = 0.25** (clamp ×4) — **PASS**.

### 3.3 Чому одні блоки за секунди, інші — понад годину?

Це **очікувана поведінка** при:

1. **Низькому / рваному хешрейті** (один або кілька майнерів, простої).
2. **Poisson-статистиці** PoW: при малій очікуваній кількості хешів на інтервал дисперсія величезна.
3. **Legacy DAA з damping 1/16:** складність не «стрибає» миттєво до нового хешрейту; після сплеску швидких блоків мережа лишається «занадто складною» на десятки блоків.
4. **Відсутності постійного фонового хешрейту** на early mainnet.

Це **не** свідчить про зламаний перерахунок `nBits` на перевіреному ланцюгу.

## 4. Реорганізації (Reorg)

### 4.1 Політика (код + `docs/REORG.md`)

- Вибір ланцюга: **max cumulative work**, не висота.
- Equal work → **залишити поточний tip** (без зайвого reorg).
- Side-блок спочатку зберігається, валідується проти **parent UTXO**.
- Reorg: disconnect (undo) → connect → tip meta; при помилці — rollback + rebuild UTXO.
- Mempool: non-coinbase з disconnect повертаються після ревалідації; coinbase — ніколи.
- Double-spend: відхилення в `validate_transaction` / spent-in-block set.
- Policy: `MAX_REORG_DEPTH = 100` (не консенсус).

### 4.2 Альтернативні блоки №227–230

Спільний предок: **h=226** `ce37fa2021d21080…`.

| 228 | **22 270 421 862** | 22 270 411 183 | ACTIVE |

- Обидві гілки мають валідний PoW.

## 7. Знайдені проблеми / зауваження

Автоматично **нічого не виправлялось**. Нижче — спостереження для рішення власника мережі.

### P1 — Нестабільний час блоку на early Mainnet  
- **Критичність:** Medium (операційна / UX), **не Critical для безпеки консенсусу**  
- **Суть:** медіана ~89 с при таргеті 600 с; періоди &lt;10 с і &gt;1 год співіснують.  
- **Причина:** низький/рваний хешрейт + Poisson + legacy damping 1/16 + зростання difficulty (~500–600× genesis біля tip).  
- **Доказ коректності формули:** 0 mismatches `nBits` на всьому активному ланцюгу.  
- **Рекомендація (без авто-застосування):**  
  - моніторинг mean/median last-30 і tip difficulty;  
  - не чіпати genesis/DAA «наживо»;  
  - після h=1500 складність «заморожується» між epoch — планувати комунікацію майнерам;  
  - будь-яка зміна DAA до/після 1500 = **скоординований soft/hard fork**, лише з окремим дозволом.

### P2 — Довге вікно до першого BTC-retarget (1500 → 2016)  
- **Критичність:** Low / Info  
- **Суть:** з h=1500 до h=2016 bits не змінюються epoch-правилом, навіть якщо хешрейт стрибне.  
- **Рекомендація:** задокументувати в README/RELEASE (окремий PR після дозволу); за потреби — окремий future fork (не зараз).

### P3 — Max supply на 0.024 MHC менше «круглих» 21M  
- **Критичність:** Info (сумісність з Bitcoin-моделлю)  
- **Рекомендація:** у публічних Specs писати «21 000 000 MHC (Bitcoin-style cap; exact sum 20 999 999.9769)».

### P4 — Compact rounding при «ідеальному» timespan  
- **Критичність:** Info  
- **Суть:** навіть при exact expected timespan `target_to_bits(bits_to_target(bits))` може дати сусідній compact (спостережено в синтетиці біля genesis bits). На Mainnet historical round-trip = 0 fails для збережених bits.  
- **Рекомендація:** залишити як є; не «виправляти» encoding без тестів сумісності.

### P5 — README Specs можуть бути застарілі щодо DAA  
- **Критичність:** Low (документація)  
- **Суть:** у коді вже dual DAA (legacy → BTC @1500); публічний README раніше описував лише W30/1/16.  
- **Рекомендація:** оновити README **після вашого дозволу** (окремо від цього аудиту).

**Critical / High consensus bugs:** **не виявлено.**

## 9. Висновок про безпеку Mainnet

**Mainnet MHCOIN 0.4.2.0 на висоті 1168 виглядає консенсусно здоровим щодо PoW і DAA.**

- Усі активні `nBits` відповідають `get_next_work`.  
- PoW (SHA-256d), MTP, POW_LIMIT, subsidy/fees — у нормі.  
- Fork-choice за накопиченою роботою коректно відпрацював на competing гілці **227–230**.  
- Reorg/UTXO/mempool/double-spend захист підтверджений ізольованими тестами.  
- Нестабільні інтервали блоків (зокрема 1155–1165) пояснюються **економікою хешрейту та повільним legacy damping**, а не зламаною складністю.

**Ризик подвійної витрати через помилковий DAA / broken work selection: низький** на перевірених даних.  
Залишковий операційний ризик early-network: довгі паузи між блоками при зупинці майнерів і, після h=1500, «плоска» складність до h=2016.
